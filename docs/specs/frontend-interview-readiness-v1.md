# Frontend Interview Readiness v1

状态：已完成  
基线日期：2026-08-15

## 1. 目标

在不扩张业务范围、不修改 AI/RAG 核心实现的前提下，补齐最影响面试演示可信度的前端可靠性证据：

1. Access Token 过期后可安全、透明地恢复会话；
2. 核心业务链路具备少量真实浏览器自动回归；
3. 商品与 AI 优化这一首要演示链路具备清晰组件边界和组件测试；
4. 中文界面、截图、README 与当前真实能力及构建数据一致。

本阶段以“可运行、可测试、可讲清楚”为停止线，不追求全站重构或覆盖率数字。

## 2. 基线与问题

- `JWT_ACCESS_TTL_SECONDS` 默认是 900 秒；当前业务请求收到 401 后直接失败，只有应用首次加载时会尝试 Refresh Token。
- Web 当前有 15 个测试文件、40 项测试，但没有 Playwright E2E。
- `products.page.tsx` 同时承载商品、SKU、库存、审计和 AI 优化入口，核心商品优化抽屉没有组件测试。
- Web 测试虽然通过，但 jsdom 会输出 Ant Design 调用带伪元素参数的 `getComputedStyle` 警告。
- 现有作品集截图中的 Agent 库存回答没有展示已经具备的业务工具调用能力；中文成果页仍直接显示部分英文状态枚举。
- 2026-08-15 本地生产构建的最大业务页面 chunk 约为 198 kB，gzip 约为 60 kB，旧材料中的约 375 kB 数据已经过期。

## 3. 范围

### FR-1：认证自动恢复

- 受保护 API 首次返回 401 时，前端调用现有 `/api/auth/refresh`。
- 同一时间出现多个 401 时，只允许一个刷新请求在途；其他请求复用该 Promise。
- 刷新成功后更新 Redux 中的 Access Token 和用户信息，并将原请求最多重放一次。
- 刷新失败后清空认证状态，由现有认证路由回到登录页。
- 不重放非 401 错误，不允许无限刷新或无限重放。
- 登录、刷新、退出接口本身不进入恢复逻辑。

### FR-2：商品核心链路模块化

- `ProductsPage` 保持组合层职责，将商品表格、商品/SKU/库存表单和审计展示拆为可独立测试的组件或 hooks。
- API 路径、DTO、权限规则、商家/店铺边界和服务端写入行为保持不变。
- AI 优化抽屉覆盖加载、生成、防重复提交、拒绝、确认写回、切换商品防旧响应覆盖等关键交互。
- 商品优化继续只生成草稿，正式写回必须经过已有人工确认。

### FR-3：核心浏览器 E2E

- 引入 Playwright，但只覆盖 3 条高价值旅程：
  1. operator 登录并进入商品 AI 优化审核链路；
  2. viewer 登录后看不到写操作入口；
  3. 中英文切换后核心导航与页面文案同步变化。
- E2E 默认使用现有 Docker 演示环境、种子账号和 Mock Provider，不调用收费模型。
- E2E 使用独立命令执行，不强制普通单元测试在没有浏览器/容器的环境中失败。
- CI 或本地完整验收可显式启动 Compose 后执行 E2E。

### FR-4：演示一致性

- 中文界面的 AI 成果状态使用本地化文案，不直接暴露 `DRAFT`、`APPLIED` 等存储枚举。
- README 使用当前生产构建可复现的 chunk 数据，并说明口径。
- 更新 AI 对话截图的制作要求：必须展示工具轨迹和来自业务服务的结果；不得用“无法连接内部系统”的旧截图证明 Tool Calling。
- 不伪造新的运行截图；若当前环境没有启动完整服务，则在演示文档中记录重拍步骤和验收内容。

### FR-5：测试稳定性

- 消除当前 jsdom `getComputedStyle(..., pseudoElt)` 噪声。
- 新增测试不得依赖真实模型或外部网络。
- 保持格式、lint、类型检查、Web 测试和生产构建通过。

## 4. 明确冻结的范围

本阶段禁止修改：

- `apps/api/src/ai/` 中的 Prompt、Provider、Agent Loop、工具选择、引用校验和 RAG 检索；
- `apps/api/prisma/migrations/20260814010000_rag_reliability_v2/`；
- RAG Development/Test Set、评估阈值和评估日志；
- AI/RAG 服务端协议和数据库模型；
- `ai-chat/` 与 `ecommerce-admin/` 两个只读参考项目。

允许在 Web 中测试和展示已有 AI 接口，但不能改变其业务语义。

## 5. 非目标

- 微前端、Module Federation、PWA、离线编辑；
- 自研组件库、完整 Design System 或全站 Storybook；
- WebSocket 替换 SSE；
- 为所有 CRUD 页面补齐同等粒度测试；
- 多 Agent 编排、工作流画布或新增电商领域；
- 以追求 100% 覆盖率为目标的低价值测试。

## 6. 验收标准

| 编号  | 验收项   | 完成标准                                                      |
| ----- | -------- | ------------------------------------------------------------- |
| AC-1  | 并发刷新 | 两个并发 401 只产生一次 Refresh 请求，均使用新 Token 成功重放 |
| AC-2  | 失败退出 | Refresh 失败后认证状态变为 anonymous，原请求不循环重试        |
| AC-3  | 请求边界 | 非 401 不刷新；每个请求最多重放一次                           |
| AC-4  | 商品模块 | 商品核心页面职责拆分，既有交互和 API 协议不变                 |
| AC-5  | 优化测试 | 生成、拒绝、确认写回和商品切换竞态至少有自动化覆盖            |
| AC-6  | E2E      | 三条指定浏览器旅程有可独立执行的 Playwright 用例和说明        |
| AC-7  | 国际化   | 成果状态在中英文界面使用对应翻译，不显示未处理枚举            |
| AC-8  | 测试输出 | Web 单元测试通过且不再出现已知 `getComputedStyle` 噪声        |
| AC-9  | 构建证据 | README 中的 chunk 描述与本次生产构建输出一致                  |
| AC-10 | 冻结边界 | `git diff` 不包含第 4 节冻结路径                              |

## 7. 实施顺序

1. 认证恢复与测试；
2. 商品页拆分与优化抽屉测试；
3. Playwright 配置和三条 E2E；
4. 状态本地化、演示说明和 README 指标；
5. 全量静态检查、测试、构建与冻结路径审计。

## 8. E2E 执行方式

E2E 使用现有 Compose 演示环境与 Mock Provider，默认不会调用收费模型：

```bash
docker compose --profile app up --build -d
npm run test:e2e:install --workspace @cross-border/web
npm run test:e2e
```

如果 Web 不在默认的 `http://localhost:5173`，可通过 `WEB_E2E_BASE_URL` 指定地址。浏览器测试使用单 Worker，避免共享演示种子数据导致并发串扰；失败时保留截图、视频和 Trace。

## 9. 验收结果

- 认证恢复新增 3 项测试：并发 401 单飞刷新、刷新失败退出、非 401/单次重放边界。
- 商品优化新增 3 项测试：生成后人工确认写回、拒绝不写回、商品切换竞态隔离。
- Web 共 46 项测试无 jsdom `getComputedStyle` 噪声；根级共 198 项测试。
- 3 条 Chromium E2E 在 2026-08-15 的 Compose API/Web 与 Mock Provider 环境中全部通过。
- 生产构建最大业务页面 chunk 为 197.57 kB（gzip 60.47 kB）。
- 冻结路径没有代码差异；Dockerfile 仅补入 seed 已经依赖的 TypeScript 文件，不改变其实现。

完整 Compose 重建同时暴露了一个不属于本阶段的既有问题：当前 RAG 演示 seed 的固定规则文档 ID 超过数据库 `id` 列长度。为遵守第 4 节冻结边界，本阶段没有修改该 seed；本次前端 E2E 使用在报错前已经成功写入的用户/商家数据，并单独启动 API、Worker 和 Web 完成验收。
